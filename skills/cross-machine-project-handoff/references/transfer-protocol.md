# 迁移协议

本协议用于把一个正在工作的 Git 项目迁移到另一台电脑。它强调可恢复、可比较和可回退；具体命令必须服从项目自己的治理文件。

内置脚本的自动闭环只覆盖 clean、单 worktree Git 仓库：`audit → pack → restore → audit → verify`。Dirty/Stash/index flags 可以被审计，但 v1.1 不自动打包恢复；必须使用本协议的专门人工方案并取得用户授权。

## 1. 迁移前冻结

1. 明确源目录、目标目录、目标操作系统和迁移窗口。
2. 列出会写入工作区的 Agent、IDE、格式化器、开发服务器、数据库和同步工具。
3. 协调或停止写入者；不要在复制过程中继续编辑。
4. 记录当前时间、HEAD、分支、`git status --porcelain=v1 -uall`、worktree、Stash、子模块和 LFS 状态。
5. 生成源清单，并将它保存在仓库外、仅当前用户可访问的位置；约定加密、保留期限和安全删除方式。

dirty worktree 是迁移输入，不是待清理垃圾。未经用户授权，不运行 `reset`、`clean`、`checkout --`、自动 stash 或自动提交。

## 2. 盘点迁移面

逐项回答：

- 哪些提交只存在本地？
- 哪些当地分支、标签、Stash 没在远端？
- 哪些 staged、unstaged、untracked 文件必须保持？
- 是否存在多个 worktree，每个 worktree 是否 dirty？
- 是否使用子模块、Git LFS、嵌套 Git 仓库或大文件？
- 哪些 ignored 文件实际是密钥或必要配置？
- 哪些 unknown ignored 文件/目录是可丢弃缓存，哪些是数据库快照、上传文件或不可重建状态？
- 哪些本地数据库、上传文件、模拟器、模型或许可证位于仓库外？
- 哪些 tracked DOCX/PDF/图片/压缩包/数据库可能含个人或业务数据，是否已获准进入交接载荷？
- 哪些依赖和缓存可依据锁文件重建？
- 哪些机器级 Codex Skill、插件和登录能力不会随仓库迁移？
- 下一台电脑靠什么文档知道正在做什么？

## 3. 选择载荷

### A. 干净且联网

适用于用户确认可以把工作形成正常提交的情况：

1. 提交应提交的改动。
2. 推送明确需要的分支和标签。
3. 目标从可信远端 clone。
4. 单独处理 Stash、秘密、本地数据和上下文。

推送后不要只依赖“命令退出成功”。记录本地精确 OID，并用不暴露凭据的 `git ls-remote <remote-name> <ref>` 确认远端 ref 指向同一 OID；把 ref/OID 和检查时间写入私有交接收据。远端 URL 只保留经遮蔽的诊断形式。

注意：普通 clone 不携带源 worktree 的 staged/unstaged/untracked 状态、隐藏 index 位或进行中的 Git 操作，也不能假定会携带 Stash、当地未推送引用、Git hooks、ignored 文件或仓库外数据。

### A2. 干净且需要可验证离线包

使用内置 `pack`。它会：

1. 重新审计并拒绝 dirty、Stash、隐藏 index、未知 ignored、额外 worktree、子模块和 LFS；
2. 拒绝尚未轮换的已暴露凭据；
3. 要求人工批准 tracked 文档/归档/数据库候选；
4. 创建并验证 `repository.bundle`；
5. 输出源清单、SHA-256 收据、结构化验证证据、交接胶囊和新会话提示词；
6. 可复制一份经用户显式确认**已加密**的敏感归档，但永远不接收或记录口令，也不把用户声明冒充密码学验证。

包目录必须在仓库外且为空。它不是公开制品：Git 历史、文件名、机器诊断和版本化数据仍可能敏感。

### B. 保持 dirty 现场

首选冻结后的单 worktree 精确载荷。可选路径：

- 对完整工作目录（包括 `.git`）制作权限受控的安全归档；目标解包后立即运行 Git 完整性检查。
- 使用 Git bundle 携带提交与引用，再使用二进制安全的 staged、unstaged、untracked 载荷恢复现场；必须逐项验证 staging 语义。
- 经用户明确授权，使用临时保存分支/WIP 提交或 `stash --include-untracked`，并在目标恢复原状态；记录它会怎样改变现场以及如何回滚。

不要把“文件内容一样”当作“现场一样”：staged 与 unstaged 的边界、删除、重命名、执行位、符号链接和冲突阶段都可能影响后续工作。

额外 worktree 含有 `.git/worktrees` 指针和各自工作目录状态。逐个迁移或先由用户收敛；不要把它们当成普通目录递归复制。

### C. 离线

至少分成三个载荷：

1. Git 对象与引用（例如经验证的 Git bundle）；
2. 非敏感工作现场与交接文档；
3. 加密的秘密/本地数据载荷。

为每个载荷记录大小、SHA-256、创建时间和接收位置。摘要可以验证传输完整性，但秘密文件的摘要不要写入公开或版本化清单。

内置收据仅记录已加密归档本身的摘要，不读取其中单个秘密文件，也不记录秘密文件摘要。

## 4. 复制守则

- 明确包含/排除规则，先 dry-run；不要使用含糊的全盘递归复制。
- 若复制完整 `.git`，先确认没有 Git 进程和锁文件写入；目标检查意外系统元数据、无效 refs 与绝对 worktree 指针。
- macOS 的 `.DS_Store` 等系统文件若落入 `.git/refs`，可能被 Git 当成损坏引用；目标必须运行 `git fsck` 和引用检查。
- Windows 与 Unix 间优先用保留二进制内容、符号链接/权限语义明确的归档工具。
- 普通载荷排除秘密与可重建缓存；分别记录如何恢复。
- 对 unknown ignored 路径只盘点名称并人工分类；不要为了判断用途而把内容打印到日志。
- 不通过聊天、终端输出、Git diff 或未加密附件传递密钥值。
- 不把密码作为压缩/解密命令的命令行参数；它可能进入进程列表和 shell 历史。使用交互输入、密码管理器或平台秘密通道。
- 凭据一旦在聊天、日志、截图或命令行暴露，即使文件被 `.gitignore`，也必须先轮换再交接。

## 5. 目标恢复顺序

1. 准备兼容的 Git、运行时、SDK、包管理器和系统依赖。
2. 恢复 Git 对象与引用，确认 HEAD/分支。
3. 恢复活跃工作现场，核对 staged/unstaged/untracked。
4. 通过安全通道恢复 ignored 私密配置，并再次执行 `git check-ignore`。
5. 导入本地数据库/外部数据，执行版本和完整性检查。
6. 从锁文件重建依赖；不要搬运另一操作系统的虚拟环境或构建目录。
7. 修复机器专属路径和平台差异。
8. 生成目标清单。

内置 `restore` 只恢复 clean Git bundle 到不存在或空目录，校验收据中的大小/SHA-256，恢复 heads/tags/其他 refs 与 HEAD，运行 `git fsck`；它不解密敏感归档。源端存在敏感路径时，预期先得到 `awaiting_sensitive_restore`，补齐后再运行最终 `audit/verify`。

## 6. 验证门

必须同时通过四层验证：

1. **传输层**：载荷摘要、文件数量/差异检查符合预期。
2. **Git 层**：源/目标清单相符，`git fsck` 通过，HEAD、分支、标签、其他本地 refs、Stash、index flags 与 dirty 现场一致。
3. **构建层**：依赖解析、静态分析和关键测试通过。
4. **产品层**：真实启动并完成一个关键用户路径；必要的数据库、服务和凭据可用。

验证证据必须使用 `passed`、`failed`、`timed_out`、`skipped`、`inconclusive` 之一。超时、跳过、未取得证据和环境不具备条件都不得记成通过。收据只保存短摘要与命令标签，不保存完整 stdout/stderr 或可能含秘密的日志。

目标还必须核对收据要求的机器级 Codex Skill/插件；项目内文件随 Git 迁移，不代表全局工具、连接器登录或浏览器会话已经迁移。

`coverage.complete=true` 与 `match` 只证明单 working tree 的 v1 可迁移比较面；不证明 ignored/仓库外状态、秘密值或应用可运行。`match_with_warnings` 表示秘密内容和机器状态仍需人工/运行验证。`inconclusive` 不通过验证门。

## 7. 切换与回退

- 目标达到验证门前，源保持只读可回退状态。
- 记录从何时起目标成为唯一写入端，避免双端分叉。
- 明确回退窗口、备份位置和源电脑退役条件。
- 用户确认后才清理临时载荷、临时分支或源副本。
- 清理前再次检查是否存在未迁移的新提交、dirty 状态或本地数据变化。
